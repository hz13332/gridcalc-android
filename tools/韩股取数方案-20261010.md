## 0. 结论摘要（先看这一节）

1. **用户报的「韩股数据没有拉取到」，最可能的直接原因不是东财挂了。**
   东财韩股接口实测**一直是好的**（HTTP 200、5 根月线、240 根日线，见 §1.2）。
   真正的结构性原因有两个，叠加起来才产生「无源」这个假象：
   - **（a）熔断键只有「源名」、没有市场/品种 → 跨链连坐**：贵金属链、步长链、韩股链共用同一个 `"东财"` 键，
     任何一条链上东财超时一次，**10 分钟内所有品种的东财腿都被滤掉**（§2.4）。
   - **（b）唯一的替补腿「腾讯」对韩股恒返回 1 根**，永远过不了 `prep` 的 ≥3 根门槛（实测 month/day 都只有 1 根，§1.3），
     于是「东财被熔断 → 只剩腾讯 → 腾讯必死 → 全灭」，而报错文案还写成 **「各行情源都没有该品种数据」**
     —— 把「我们没取到」说成「你没这个品种」。
2. **推荐（两步走）**：
   - **第一步 = 路线 C（东财单源加固：熔断键隔离 + 文案 + 东财备用 host）**
     零新增源、零口径变化、**正常路径请求数不变**，直击上面两个原因。
   - **第二步 = 路线 B（把第二腿「腾讯」换成 Naver）**
     唯一一条**在中国大陆出口实测可用**的独立源；替补模式下 **请求成本零增量**。
     代价：Naver 的收盘价口径与东财**系统不同**（≤0.9%，8/8 天命中，§3-B 风险 ①），需用户拍板。
3. **明确不推荐路线 A（恢复 Yahoo .KS 兜底腿）**：`005850.KS` 从**中国大陆出口实测 403**
   （Yahoo 2021-11-01 起对中国大陆整体停服），而 App 是在用户手机上跑的。这条腿在用户网络里大概率恒失败。
4. **附带核实**：`MktSuggest.KRNAME` 11 条里 **4 条错**（含任务点名的 `005850 → LG电子`），
   另有 `ENALIAS` 的 `"KIA" → "000240"` 错。**只列不改**，见 §6。

## 2. 现状的取数与限流机制（决定「请求成本」的关键）

### 2.1 替补模式 = 后面的腿根本不发请求

`raceOk()`（≈L962）的语义是**顺序替补**，不是竞速：按 pool 顺序依次试，
**第一条 `prep` 成功的腿即胜出，后面的腿标 skipped、一个请求都不发**。

⟹ **推论（后面反复用）：给腿链「加一条兜底腿」，在正常路径上请求数不变。**
只有第一条腿失败时才轮到第二条 —— 而韩股现在这个「第二条」位置**本来就有一个请求**，
只是它发给了一个**必死的源**（腾讯恒 1 根）。

### 2.2 两道熔断

| 表 | 触发 | 冷却 | 键 | 位置 |
|---|---|---|---|---|
| `SRCBAD` | 抛异常（网络/超时/HTTP 非 2xx） | **10 分钟** | **源名字符串** | ≈L847 |
| `SRCBAD_SOFT` | 响应成功但没数据（限流典型表现） | **20 秒** | **源名字符串** | ≈L868 |

### 2.3 「不切源」墓碑与现状的矛盾

见 §1.2 末。这条矛盾对本调研的意义是：**任何"要不要加腿"的决策，都不能引用"用户要求单源"当挡箭牌**——
因为代码现状早就是多腿了，用户也从来没看见过单源行为。

### 2.4 🔴 根因候选：熔断键只有「源名」，没有市场/品种 → 跨链连坐

```
raceOk():  catch (_: Exception) { srcBadMark(nm); threw = true }      // nm = 腿名字符串
fetchStocks():  val rest = legs.filter { !srcBadSkip(it.first) && !softSrcSkip(it.first) }
                val pool = if (rest.isNotEmpty()) rest else legs
```

- 三条链用的都是**同一个字面量键** `"东财"`：贵金属 `fetchMetals()`（≈L1332）、步长链（≈L1470 附近）、韩股 `stockLegs()` kr（≈L1040）。
- ⟹ **黄金/商品那边东财超时一次 → 韩股的东财腿被 10 分钟硬熔断**（反之亦然）。
- ⟹ 此时 `rest` 里只剩「腾讯」→ `pool = [腾讯]` → **这一轮东财根本不发请求**，
  腾讯恒 1 根 → 全灭 → 抛 **「各行情源都没有该品种数据」**。
- 只有当**两条腿同时**被熔断时，才会走到 `pool = legs`（试全部腿）那条回退。
  也就是说 2026-10-07 那个「泛化修无源」的补丁（注释见 ≈L1070-1072，明确点名了「韩股腾讯恒 1 根」）
  **对韩股这个场景不够用**：它只在"两腿都脏"时生效，而实际最常发生的是"只有东财脏"。
- 结果还有一点抖动：腾讯被软熔断后 20 秒内 `rest` 变空 → 才会重新试东财 →
  表现为「每隔 20 秒有一次机会，其余时间必失败」。

> ⚠️ 这是**根因候选**，不是本任务要改的东西（限流闸是 t6 的 owner）。
> 列在这里是因为它直接决定 §5 的推荐顺序。

**返回格式（★ 三个坑，接入时必须处理）**

```
 [['날짜', '시가', '고가', '저가', '종가', '거래량', '외국인소진율'],
["20261008", 50600, 50900, 49850, 50000, 66602, 16.05],

```

1. **不是合法 JSON**：单引号、`\r\n\t` 缩进、韩文表头 ⟹ `JSONObject(s)` 会抛异常，必须用正则/逐行解析。
2. **列序是「标准 OHLC」**：`日期, 开, 高, 低, 收, 量`（**o,h,l,c**）。
   与东财（`日期, 开, 收, 高, 低`）、腾讯（`日期, 开, 收, 高, 低`）**都不同**，极易搞反 —— 必须写死注释。
3. **日期是 `yyyyMMdd`**（`20261008`）⟹ 现有的 `parseNasdaqDate()`（只认 `MM/dd/yyyy`、`yyyy-MM-dd`、`MMM dd, yyyy`）
   **认不出来**，要新增一档。

**改动面**
- `MktData.kt` → `stockLegs()` kr 分支：把 `"腾讯" to {...}` **替换**为 `"Naver" to { fetchNaver(sym, tf, count) }`
- `MktData.kt` → **新增** `fetchNaver()`（返回 `listOf(VendorKs("NV", ks))`），内部：
  新增 `yyyyMMdd` 日期解析 + 单引号数组解析 + 按 `prep` 门槛（≥3 根）返回空表示"这条腿失败"
- `MktData.kt` → `vendorName()`（≈L1812）加 `"NV" -> "Naver"`（不加也能跑，`else -> v` 会原样显示 `"NV"`）
- 腿名字符串 `"Naver"` 同时是 `SRCBAD` 的键 ⟹ **全仓统一用一个写法**（建议 `"Naver"`）

**风险**
- 🔴 **① 收盘价口径不同（本方案最大的代价，必须让用户知情）**

  实测同一天，Naver 的 **O/H/L 与东财/腾讯/Yahoo 逐位一致，但 C（收盘）系统性不同**：

  | 日期 | 东财(177.005850, fqt=1) o,c,h,l | Yahoo 1d o,h,l,c | Naver day o,h,l,c | 收盘差 |
  |---|---|---|---|---|
  | 2026-10-08 | 50600, **50300**, 50900, 49950 | 50600, 50900, 49950, **50300** | 50600, 50900, 49850, **50000** | 0.60% |
  | 2026-10-07 | 51700, **50900**, 52000, 50700 | 51700, 52000, 50700, **50900** | 51700, 52000, 50400, **50600** | 0.59% |
  | 2026-09-30 | 50000, **49300**, 50100, 49000 | 50000, 50100, 49000, **49300** | 50000, 50100, 49000, **49650** | 0.71% |
  | 2026-09-29 | 50200, **49700**, 50400, 48900 | 50200, 50400, 48900, **49700** | 50200, 50400, 48900, **49650** | 0.10% |

  三星（005930）同样：8 个交易日 **8 天收盘价都不同**，最大 **0.9%**（2026-09-29：东财 272500 vs Naver 275000）。

  **成因（已定位到可信解释）**：两个源取的是**不同交易时段的价格**。
  - 东财/腾讯/Yahoo 取的是 **KRX 正规交易时段（정규장）收盘价 —— 15:30 收盘竞价**：
    Yahoo `meta.regularMarketTime = 1791441002` = **2026-10-08 15:30 KST**；东财、腾讯 `qt`、Yahoo 三源同值 `50300`。
  - Naver 取的是**当天最后一笔（盘后/替代交易所时段）价格**：
    `m.stock.naver.com/api/stock/005850/basic` → `closePrice:"50,000"`、`compareToPreviousClosePrice:"-900"`、
    `localTradedAt:"2026-10-08T20:34:33+09:00"`（**20:34 KST**，远在 15:30 之后）。
  - 韩国本地源一致：Daum `finance.daum.net/api/quotes/A005850` → `tradePrice:50000`、`prevClosingPrice:50900`（昨收与东财一致）。
  - **⟹ 两个韩国源（Naver/Daum）说 50000，三个国际源（东财/腾讯/Yahoo）说 50300。**
  - 成交量口径也不同：东财 `65310` vs Naver/Yahoo `66602`（东财偏小约 2%）。

  **为什么这条对本案特别要紧**：用户报的 4 个问题里第 ④ 个就是「距支撑数值在复用路径与网络路径间**跳变**」。
  引入一个收盘价口径不同的兜底源，等于在「东财挂掉」时让图上最后一个收盘价和距支撑数字整体跳 0.1%~0.9%。
  用户会在图例上看到源名变成 `Naver`，但数字本身会变 —— **必须先让用户拍板「兜底时口径允许不同」**。
- 🟡 **② 未公开接口**：`siseJson.naver` 没有文档、没有 SLA，是韩国散户工具圈长期在用的非官方端点；格式可能变。
  ⟹ 接入时**解析必须"宽松失败"**：解析不到就返回空（= 这条腿失败），绝不能让异常冒泡影响东财那条腿。
- 🟡 **③ 非 JSON**：见上面三个坑；解析代码比东财腿长，是新代码面。
- 🟢 限流风险低：只在东财失败时才会被调用（见成本）。

**请求成本**：**零增量**。
- 正常路径：东财成功 → Naver 一个请求都不发（替补模式），**1 次/品种，与现在完全相同**。
- 失败路径：东财失败 → Naver 1 次，**仍是 2 次/品种**（现在那次是打给必死的腾讯）。
- 对东财的压力：**0**（不同 host，反而省掉一次腾讯请求）。
- ⛔ **绝对不要"叠加"成 `[东财, Naver, 腾讯]`**：失败路径会变成 3 次，比现在 +50%。

### 路线 C：东财单源加固（熔断键隔离 + 文案 + 备用 host）★ 推荐的第一步

**可行性证据（实测）**

| URL | DNS | 结果 |
|---|---|---|
| `push2his.eastmoney.com/api/qt/stock/kline/get?secid=177.005850&klt=103...` | `120.79.123.125`, `120.79.243.12` | **HTTP 200**，3 根 |
| `1.push2his.eastmoney.com/...`（同路径同参数） | **`117.184.40.129`（另一台前端机）** | **HTTP 200**，3 根 |
| `2.push2his.eastmoney.com/...` | `120.79.123.125`, `120.79.243.12` | **HTTP 200**，3 根 |
| `3.push2his.eastmoney.com/...` | `120.79.123.125`, `120.79.243.12` | **HTTP 200**，3 根 |
| `push2his.eastmoney.com.cn/...` | `61.152.229.228` | TLS 失败（证书不可信）—— **不要用** |

⟹ 东财有**多台前端机**，`1.` 前缀是一台独立 IP。**同接口、同参数、同口径、同数据**。

**改动面（三件事，都是小改）**
1. **熔断键按「源 × 市场」隔离**（直击 §2.4 的跨链连坐）：
   `raceOk()` 的 `srcBadMark(nm)` / `srcBadSkip(name)` 调用处，把键从 `"东财"` 改成 `"东财|kr"` 这类带市场后缀的键；
   或最小改法：**给腿名带上市场**（`"东财"` → `"东财·韩股"`），键自然隔离，UI 侧过 `vendorName()` 时再还原显示名。
   ⚠ 这条与 t6（限流闸）高度重叠，**由 t6 owner 决定最终形态，本文件只给证据与判据**。
2. **文案说实话**：`fetchStocks()`（≈L1085-1088）现在只有两句 ——
   `if (win.anyNoData) "各行情源都没有该品种数据" else "各行情源都不可达,请稍后重试"`。
   但「东财被熔断跳过、只剩一条必死腿」既不是 noData 也不是 netFail。
   ⟹ 建议新增第三类：**「东财限流冷却中（还有 N 秒），已跳过；当前无可用兜底源」**，
   并且把"被熔断跳过的腿"如实显示在源状态行（`lastLegs` 里已经标了 `skipped`，只是文案没利用）。
3. **东财备用 host 重试一次**：`fetchEastmoney()`（≈L1229）在**抛异常**时换 `1.push2his.eastmoney.com` 再打一次
   （只在失败时，不是每次都打两个）。

**风险**
- 🟢 低：同源、同接口、同口径，**图上数字一个都不会变**。
- 🟡 不解决「东财整体被限流 / 出口 IP 被封」的极端情况 —— 那是路线 B 的职责。
- 🟡 host 轮换只是缓解「某一台前端机抽风」，**不要做成"连环重试"**：两个 host 都失败就必须退避，
  否则正好撞上用户「不要频繁打」的红线。

**请求成本**：
- 正常路径：**不变**（1 次/品种）。
- 失败路径：由「东财(主) + 腾讯(必死)」变成「东财(主) + 东财(备)」= 仍是 **2 次/品种**，
  但对**东财**的请求 +1、对腾讯的请求 −1（净总量不变）。
- 熔断键隔离会让**正常路径的请求数不变、失败路径的重复请求大幅减少**（不再有 10 分钟内"每次都白打一次必死腿"）。

## 4. 请求成本对照表（用户硬约束：不要频繁打、不要被限流）

| 方案 | 正常路径（东财成功） | 失败路径（东财失败） | 对**东财**的额外压力 | 口径是否一致 | 中国大陆可达 |
|---|---|---|---|---|---|
| **现状**（东财 + 腾讯） | 1 次 | 2 次，**且必然全灭** | 0 | ✅ | ✅ |
| A 东财 + Yahoo | 1 次 | 2 次 | 0 | ✅（逐位一致） | ❌ **403** |
| **B 东财 + Naver**（替换腾讯） | **1 次（不变）** | **2 次（不变，且能成）** | 0 | ⚠️ 收盘价差 ≤0.9% | ✅ |
| B′ 东财 + Naver + 腾讯（叠加） | 1 次 | **3 次（+50%）** | 0 | ⚠️ | ✅ |
| **C 东财 + 备用 host**（替换腾讯） | **1 次（不变）** | **2 次（不变）** | **+1（换台机器）** | ✅ 完全一致 | ✅ |
| C′ 东财单腿（只删腾讯） | 1 次 | **1 次（最省）** | 0 | ✅ | ✅ |

**关键结论（写进决策依据）**：
> 替补模式下，「加一条兜底腿」在**正常路径上是零成本**，只有第一条腿失败时才花第二次请求。
> 而**这次请求现在也在花** —— 花在一个永远不可能成功的腾讯腿上。
> 所以路线 B/C **不是"增加抓取频率"，而是"把已经花掉的那一次换成能用的"**。
> 真正会加剧请求的是**叠加**（B′）和**连环重试**，这两种都不要做。

**明确推荐：先做路线 C，再做路线 B。不做路线 A。**

2. **东财失败时最多允许几次请求？** 建议硬上限 **2 次/品种**（现状就是 2 次），任何方案都不得超过。
